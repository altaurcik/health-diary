# Telegram и развёртывание через GitHub Actions

Развёрнуто 2026-09-26 после отдельного подтверждения владельца.
Первый production workflow [36268694502](https://github.com/altaurcik/health-diary/actions/runs/36268694502)
прошёл целиком: тесты, сборка, SSH deployment и публичный HTTPS health.
Установлен релиз 22d1c05; последующие push в main автоматически проходят тот же путь.
Первоначальный отказ auto-review снят явным подтверждением пользователя;
это исторический этап, а не текущая блокировка.

Подтверждены HTTP 200 для сайта/health и 401 для дневника без сессии.
На production синтетическая проверка подтвердила вход по подписанным данным,
запись/чтение, изоляцию двух пользователей и CAS 409; тестовые аккаунты удалены,
сообщений от них не отправляли. Реальный запуск в клиенте Telegram и доставка
личного напоминания пользователю ещё требуют пользовательского /start/разрешения.

## Схема

- Бот: `@bpjournalbot`; токен не включать в Git или frontend.
- URL: `https://healthnote-bot.duckdns.org:8443`.
- На сервере уже есть nginx; 443 занят Xray/VPN. Используем отдельный nginx
  vhost на 8443 и Certbot HTTP-01 через существующий 80. VPN не меняем.
- PostgreSQL: существующая `survival_analytics`, отдельная схема `health_diary`.
  Новая база не создаётся. Служебная роль/Unix-пользователь `health-diary`.
- `backend/server.py`: API на `127.0.0.1:8791`, polling Telegram и планировщик.
  Python 3.12, stdlib и уже имеющийся на сервере psycopg2. Systemd ограничивает
  память и права. Никакого npm/node runtime на VPS не требуется.
- Таблицы `users`, `deliveries`, `bot_state`: пользовательский JSON-дневник с
  revision, задания доставки с уникальными ключами, offset polling.
- Frontend остаётся React/Vite; `CloudGate.jsx` проверяет вход через Telegram,
  вне Telegram production показывает ссылку на бота и отдельное демо.
  Dev-сайт на 127.0.0.1 по-прежнему работает локально.

## Проверки и безопасность данных

Backend проверяет HMAC Telegram initData и срок auth_date; подписанная сессия
действует 12 часов и хранится только в памяти страницы. Все операции с дневником
ограничены Telegram ID из проверенной сессии. PUT проверяет revision: конфликт
возвращает 409 без перезаписи. В API нет доверия к переданному клиентом user_id.

В Telegram-режиме записи, профиль и будильники сохраняются на сервере;
существующие локальные измерения можно перенести JSON-файлом в профиле.
Импорт добавляет только новые id, настройки не заменяет. LocalStorage не
используется как серверный аккаунт. Тема пока также имеет локальное предпочтение.

Планировщик проверяет время каждые 15 секунд; окно догоняющей отправки — 10 минут.
Для «Всё» давление и вес имеют отдельные задания/сообщения. Задание захватывается
в БД до отправки; при сетевом неопределённом результате повтор не выполняется,
чтобы не дублировать сообщения (доставка at-most-once, возможен пропуск).
Отправка доступна после /start или разрешения писать. 403 отключает доставку
пользователю до нового разрешения. Сообщения не содержат значений измерений.

## GitHub Actions

`.github/workflows/delivery.yml` запускается на push main, pull_request и вручную.
Проверки: 26 тестов frontend, 8 model-тестов backend, HTTP/PostgreSQL integration
в отдельном одноразовом CI-контейнере (изоляция пользователей, CAS, валидация,
уникальная доставка), Telegram UI smoke, Vite build.

Артефакт содержит только собранный frontend, backend и SHA коммита. Actions
закреплены по проверенным SHA. Deploy выполняется только для main после тестов,
если repository variable `DEPLOY_ENABLED=true`, в environment `production`.
Секрет `DEPLOY_SSH_KEY` — отдельный ключ пользователя `health-deploy`.
Проверка SSH host key обязательна (`ops/known_hosts`). Временный файл ключа
удаляется после job. Токен бота в GitHub Actions не требуется.

Серверный SSH-ключ ограничен forced command: только root-owned
`/usr/local/sbin/health-diary-deploy`, без shell/forwarding/PTY. Wrapper проверяет
состав и размер архива, сохраняет backup схемы, выполняет SQL от имени роли
дневника, атомарно переключает `current`, перезапускает только health-diary и
проверяет API. При неуспехе восстанавливает предыдущую ссылку/версию кода.
Миграции схемы должны оставаться обратно совместимыми; автоматического отката
данных из backup нет.

## Первоначальная настройка (выполнена; справочник для восстановления)

1. Создать локально отдельный SSH deploy key; публичную часть установить на VPS,
   приватную — зашифрованным repository secret `DEPLOY_SSH_KEY`.
2. Создать root-only `/etc/health-diary/app.env` (0600) по `ops/app.env.example`:
   BOT_TOKEN, случайный SESSION_SECRET, APP_URL, DSN. Секреты не выводить.
3. Передать bootstrap-файлы из этого checkout. `ops/bootstrap.py` устанавливает
   certbot при необходимости, пользователей/роль/схему, ограниченный SSH-доступ,
   systemd unit, nginx vhost, сертификат и автообновление; разрешает 8443 в ufw,
   если firewall активен. Другие приложения и порт 443 не перенастраивает.
4. Проверить `ops/configure_bot.py`: getMe должен вернуть bpjournalbot; при
   существующем webhook скрипт останавливается. Настраиваются меню Mini App и /start.
5. Включить `DEPLOY_ENABLED=true`, запустить workflow для main; проверить deploy,
   публичный HTTPS, API без авторизации (401), вход в реальном Telegram и запись.
6. Пользователь открывает бота, нажимает «Начать» и настраивает напоминание.
   Реальную доставку проверять только на пользователе, который её запросил.

Серверные факты и даты проверок — в общей `../SERVER_MAP.md` вне репозитория.
Production уже подтверждён успешным workflow и HTTPS-проверкой.
При изменении служебных root-owned bootstrap/wrapper-файлов одного push
недостаточно: они обновляются отдельно через административный SSH.
Прикладные backend/frontend/schema релизы устанавливаются только Actions.

Локальный `ops/configure_actions.py` использует существующий Git credential helper,
шифрует deploy-ключ PyNaCl и настраивает Actions. Вспомогательная зависимость
устанавливается только в `.cache/deploy`; локальные staging-копии приватного
SSH-ключа и токена после настройки удалены. Токен бота хранится только на VPS;
приватный deploy-ключ — в зашифрованном GitHub Secret.


## Исправление запуска на Android — 2026-09-27

Сценарий владельца: iPad с полным VPN открыл и сохранил профиль, телефон с
раздельной маршрутизацией показывал обычную страницу запуска даже через кнопку бота.
Подтверждено наличие сохранённого состояния и корректного menu button, без
чтения личных данных. Недоступность telegram.org на телефоне — вероятная причина,
не доказанный факт о блокировке РКН.

Причина ошибочного экрана в коде: отсутствие внешнего SDK приравнивалось к
запуску вне Telegram; ссылка t.me не использовала native navigation. SDK теперь
поставляется неизменённым с нашего origin; источник и SHA256 в vendor/README.md.
Внешняя загрузка telegram.org при старте не нужна. Raw launch hash используется
только для передачи initData в API с прежней HMAC-проверкой. Ошибка загрузки/
отсутствия initData отображается отдельно и предлагает перезапуск. При наличии
bridge переход к боту использует native event и закрывает проблемное окно.
Демо при ошибке входа не предлагается, чтобы не путать пользователя с личным дневником.

35 frontend-тестов: отдельная VM проверяет официальный SDK в Android-контексте
без сетевого доступа; тесты покрывают отсутствующий SDK, исходные параметры,
позднюю инициализацию, переход к боту и отсутствие доверия к старой SDK-сессии.
Реальный телефон с маршрутизацией владельца остаётся необходимой проверкой.
